Pyhopper Web is trying to turn the core Pyhopper system into a browser-based parametric modeling workspace: part Grasshopper-style visual programming tool, part lightweight geometry viewer, part AI-assisted graph editor. The user’s real job in the product is to build a “definition” out of components, connect dataflow between nodes, compile that graph into Python, and generate a 3D result that can be previewed as a GLB model in the same screen. It is not structured like a conventional website with pages, navigation, and content sections; it behaves more like a desktop design instrument dropped into the browser. The app auto-hydrates into an active project, persists definitions locally, supports multiple saved definitions, and treats each project as a named computational canvas with its own graph snapshot, generated code, rendered model, and selection state.

The UI/UX is strongly canvas-first and spatial. The entire viewport is a full-screen composition: a live 3D scene sits underneath, and on top of it floats a large frosted-glass panel containing the node editor. In the upper-left there is a small HUD label that simply brands the tool as Pyhopper Web and describes the environment as a Three.js viewport plus XYFlow canvas, which sets the tone as a technical instrument rather than a consumer app. The 3D scene uses a pale industrial palette with a soft gray-blue gradient background, a large infinite grid, and orbit controls, so the first impression is closer to CAD or computational design software than a typical web app. The graph editor itself lives in a movable, resizable translucent panel with rounded corners, soft blur, and subtle borders, as if it is a lightweight drafting surface hovering above the model space. The overall aesthetic is clean and modern but intentionally understated: warm off-whites, cool grays, dark teal accents, and occasional amber selection states, with almost everything rendered as glassy utility surfaces instead of heavy chrome.

The main user flow is: create or open a definition, add components, wire them, inspect outputs, then compile/export. Definitions are managed from the floating panel header, where the user can create a new definition, load a test definition, or open a definitions browser that acts like a project switcher with search, rename, delete, and a grid of saved cards. Inside the canvas, there are two parallel ways to add nodes: a tabbed component browser pinned across the top center for browsing by tab and category, and a faster contextual search that opens on double-click exactly where the user clicked, letting node creation feel local and direct. That search also supports a number-slider shortcut, which matters because sliders are a first-class interaction pattern. Once nodes exist, the graph behaves like a serious editor: users can drag, multi-select, copy, paste, reconnect edges, delete, select all, and clear with Escape. Right-clicking a node opens a context menu for toggling preview visibility; right-clicking a port opens data-tree operations like Graft, Simplify, Flatten, Reverse, and Reparametrize, which is a very Grasshopper-like detail and should probably remain central in any redesign. The node vocabulary itself has distinct personalities: ordinary components are compact rectangular blocks with tiny handles and a vertical title strip; number sliders are horizontal control nodes with a direct manipulation ruler; panel nodes are bright yellow, resizable, and intentionally reminiscent of legacy Grasshopper panels, displaying branch paths and item values in a monospace table. There is also a minimap in the bottom-left and a compact export control stack in the bottom-right of the canvas panel, including a compile/export action, a toggle to switch from graph view to generated Python view, and a settings popover for realtime generation.

The assistant experience is the other major UX layer, and it is more like an always-available copilot than a side feature. A floating circular chat trigger sits at bottom-right above everything; opening it expands a tall, nearly full-height glass chat window pinned to the right edge of the viewport. The chat has two modes: the live conversation and a searchable history view with saved sessions, rename/delete actions, and auto-generated titles based on the first user prompt. The AI receives not just the current message thread but the active project context, stored graph snapshots, and exported state, and it can return both text and direct canvas updates, meaning the intended flow is conversational design assistance, not just Q&A. In practice, the ideal user journey is: sketch a graph visually, orbit the model to inspect it, ask the assistant to refine or generate parts of the definition, watch the canvas update, export to regenerate geometry, then switch to code view to inspect the emitted Python. For a Claude design prompt, the key UX truth is that Pyhopper Web is not a dashboard and not a chat app with a canvas attached; it is a computational design cockpit where the graph is the primary workspace, the 3D viewport is the immediate feedback surface, and the assistant is a high-context collaborator layered on top of both.
